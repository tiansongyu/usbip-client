# Confirmed terminal actions and preferences

Install the test-only pinned decoder from `../qemu_tui/requirements.txt` into a
virtualenv, then run its Python:

```sh
python3 -B scripts/qemu_tui_actions/run.py --family ipv4 --kernel 6.8.0-106-generic --timeout 600 --evidence /tmp/new-action-evidence
```

Only disposable Native QEMU guests are affected. No host USB passthrough occurs.
Nineteen actual UID1000 product PTYs per pair save/reload/override preferences,
show a real checked-file permission error, confirm all six fixed-profile starts,
stop the exact incoming HID session, and stop four actual jobs. Test key timings
are bounded fixture scheduling, never proof of completion. Actual guest journals,
requested identities, UI frames, kernel enumeration/I/O, exact cleanup proofs and
wait/UID/capabilities/executed ELF/termios receipts decide the result.

Each Start receipt file is a **real replayed RetryStart** for the request created
by the TUI. That safe query cannot create a new job. Before/after requests must
show exactly one new matching UID/profile/job and no changes from retry. No fake
Started/StopAccepted JSON is generated. All original 264 managed kernel,
identity/proof, two-epoch recovery and three-round HID/FTDI/ciphertext checks are
retained. This UI-driven scenario does not claim the original CLI-start path ran
unchanged; `qemu_tui/run.py` remains a separate default/invocation-only regression.

The settings file is real mode0600, under a caller-owned0700 directory. A
relaunch displays saved values; explicit CLI overrides leave the saved bytes
unchanged. A parent chmod to0644 triggers a visible failed Save without changing
bytes, then the disposable root fixture restores the test file's mode. This is
not a permanent-FS-blocking, power-loss or unknown-start-reply gate.
