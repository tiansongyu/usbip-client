Default backend

Keep USB requests
in the Linux kernel.

RustUSB handles discovery, policy and connection management. Linux usbip_host, usbipd and vhci_hcd carry the Native USB data path.

  • Export and import approved devices
  • Inspect sessions and disconnect owned ports
  • Run the CLI without root privileges
Native setup ↗
Discover a remote deviceCLI example
# After administrator setup
rustusb discover 192.0.2.1 --json

# Use the actual returned Bus ID
rustusb attach 192.0.2.1 1-2
rustusb sessions

# Use the port from sessions
rustusb detach 0

Example address and identifiers. Requires approved devices, a running helper and a managed secure network.

Optional · rust-backend

Start with
a virtual USB device.

The Rust server provides fixed HID and CDC ACM profiles. Use them to explore protocol behavior and Linux VHCI interoperability without exporting a host USB device.

  • Fixed keyboard and serial profiles
  • Bounded USB/IP protocol handling
  • Cooperative SIGINT / SIGTERM shutdown on Unix
Virtual server guide ↗
Explore the virtual serverCLI example
cargo build --release --locked \
  --workspace --features rust-backend

target/release/rustusb \
  virtual-server --help

# Listen on loopback for local exploration
target/release/rustusb virtual-server \
  --listen 127.0.0.1:3240

The server is a developer interface. See the guide for control input, profiles and guest setup.

Experimental · physical-nusb

Explore a Rust
USBFS server.

A restricted helper grants device file descriptors to the ordinary-user server. Persistent original-state records block new grants while a previous grant remains unresolved.

  • QEMU HID, FTDI and ECM evidence
  • Verified cooperative completion
  • Explicit administrator reconciliation
Physical server guide ↗
Inspect experimental capabilitiesCLI example
cargo build --release --locked \
  --workspace --all-features

target/release/rustusb \
  physical-server --help

# Administrator-only record inspection
sudo /usr/local/bin/rustusb \
  --json physical-pending

Requires an installed all-features helper and explicit device policy. Original-driver recovery requires a separate opt-in policy and unchanged configuration.

Read the tested revisions and evidence ↗

Default and all-features builds each boot one guest. The actual ordinary-user CLI observes keyboard insertion, interface driver changes, removal and reinsertion with a new generation. Complete batches and the actual worker exit are checked. These are local inventory tests; USB/IP redirection and real hardware retain separate evidence.

Both binaries pass SIGINT, real stdout backpressure with SIGTERM and a closed-output error. Earlier hostname fallback, authentication limits and the full acceptance history keep their tested versions and boundaries.

The observation guide explains live inventory and stale data. The application service provides independent jobs and session audit; data-link health measures the actual connection. Metadata and logs do not prove USB release.

Continuous remote catalog observation has separate validation: 903 software executions and two Native paired QEMU runs. A busy entry disappearing does not mean physical unplug, and an observer join does not prove USB cleanup.

Know the current boundaries

This is a development preview. Real-device acceptance is pending, and discovering a device does not establish compatibility.

  • Secure commands require administrator-provisioned mutual TLS and device authorization. Legacy commands still need an administrator-managed secure network.
  • Opt-in crash recovery is limited to the saved device state; broader recovery and full security acceptance remain unfinished.
  • An optional terminal preview is available. A native desktop preview is also available. Explicitly delegated fixed-profile automatic rules have QEMU evidence for Native/USBFS local rules and virtual remote import. Native GUI rule editing now has dual-stack QEMU evidence for fixed-profile edits, real lost replies and original-UUID queries. Opt-in durable refusals add restart-safe service queries and explicit original-draft restoration. Frontend process recovery preserves confirmed request identities and the last issued draft for explicit original queries after restart. Experimental Ubuntu packages now have complete amd64 installation lifecycle evidence on both Ubuntu versions. Separate ARM64 cold-installation tests cover both releases with actual GUI close, guarded same-source upgrades and real reboots. Separate installed Native/USBFS data tests cover HID/FTDI I/O and live upgrades on IPv4/IPv6. Framed-close regressions and coordinated preview migration now pass; upgrade both framed-v2 endpoints before restarting imports. A mixed new-client/old-server run remains failed, and the original intermittent import failure’s cause remains unproven. Unconfirmed forms, power-loss durability, storage sharing, ISO, full GUI acceptance, dynamic/physical remote rules, ARM USB I/O and Windows USB support remain planned or unvalidated.
