# Diagnostic export: Native/configuration source preflight

2026-10-24. Source: `46cd950affb0c949b164d0051be7bf70f365fac9`. This is a read-only proposal for requirement 4.11, not an implementation or new acceptance result. I authored several existing harnesses; this is source analysis, not an independent implementation audit. No product CLI, Cargo, build, QEMU, USB operation, or Git mutation was executed. All deliverables are under this report's `/tmp` directory. `sources.json` contains 31 exact source copies, SHA-256, and comparison with this HEAD's Git blobs.

## Recommended first deliverable

Add a bounded, versioned diagnostic **projection** of the current local Native/helper observations. Reuse their observation functions, but do not serialize the private CLI `Doctor` or arbitrary JSON from `Status`, and do not collect raw configuration, devices, session journals, stderr, environment, or proc command lines. This reaches a useful first diagnostic-export slice without importing the Rust USB engine, making a remote connection, or acquiring a helper capability. Optional application/configuration diagnosis should be explicitly feature-gated and separately scoped, rather than making every ordinary diagnostic load credentials.

The current `doctor` result is an observation, not a readiness/security/USB certificate. Keep `network_security_verified=false`, `hardware_test_performed=false`, and distinguish available / missing / denied / unsupported / unknown. Successful export means the report was collected and written; unavailable components are data, not proof that USB work failed. An interrupted/failed export must not masquerade as a complete report.

## Configuration diagnosis gap and bounded implementation option

`transport::config::load_server/load_client` (`config.rs:68/86`) are startup loaders, not general diagnostic inspectors. They enforce the **actual dedicated nonroot broker UID** (`Context::broker:308`), open private key/CA/chain bytes (`credentials:481`), and construct TLS settings. They do not bind/connect/acquire USB, but calling them as root/operator would either deny by design or unnecessarily load secrets. `service::LoadedConfig::load:194` repeats this boundary and loads every configured profile; it must not be called to “test configuration” in a generic export command.

`service::Manifest::read:87` + `validate:98` is the existing public-only entry point: it calls `transport::config::read_root_document:104`, verifies root-owned protected file/ancestors and bounded strict JSON, does not load keys or open a listener. Its successful **value** still needs the projection above. For the default Native build, the service and transport crates are optional; do not make this path mandatory simply to inspect a manifest.

If current configuration diagnosis is required in the same slice, add a small **public metadata-only inspector behind secure-transport**, reusing the trusted bounded read and strict schema decoder inside transport rather than reimplementing a looser parser in CLI. Return a closed summary (kind/schema/link protocol/pool counts/permission stages) and explicit `credentials_not_loaded` / `handshake_not_performed`. Avoid reading key bytes and avoid promising certificate validity/chain/name/pin/revocation success. Metadata-only key inspection, if added, needs actual opened-descriptor identity checks, not `exists()`; it must remain optional and cannot become an arbitrary path traversal/read API over helper or service IPC. A report that omits this feature should state `not_requested` or `feature_unavailable`, not mark config valid.

Existing transport errors are already fixed static categories/field labels (`transport/lib.rs:44`; `config.rs:322 io_error`), and fixtures test no path/input-byte exposure. Still map them explicitly to a report enum instead of using text as a schema. Existing loaders' synchronous filesystem work must remain off the async executor, with its real blocking owner joined; a timeout cannot pretend a filesystem operation stopped.

## Minimal API/dependency proposal (not implemented)

A CLI-owned `DiagnosticExportV1` can contain `schema_version`, package/feature facts, bounded `system`, two fixed module checks, two tool check IDs, sanitized helper result, and explicit scope fields. A pure `project_native(&NativeDiagnostics)` / `project_helper(&HelperDiagnostics)` performs the narrow mapping; the observation functions stay public at their existing layers. No new privileged API, config mutation, capability request, or recovery operation is needed.

Current CLI `default=[]`; `secure-transport` adds only optional transport/service; Rust engine is enabled only by `rust-backend`, and USBFS by `physical-nusb` (all three Cargo manifests copied). Keep this graph. A default-built diagnostic should report feature unavailable instead of linking Rust engine or starting an agent. No unconditional transport/service import in the CLI diagnostic module.

For an output file, choose an explicit user-selected destination with create-new/no-follow semantics, private0600 permissions, bounded complete JSON and real write/flush errors. Do not overwrite/symlink-follow an existing target or recursively collect arbitrary files. If atomic publication is chosen, specify failure behavior for both temporary file and destination and do not include their paths in the report/error payload. Global file logging may legitimately write its own log; no-USB-side-effect is the actual contract. For stdout, avoid silently reusing synchronous `output` (main.rs:271) if bounded cancellation/backpressure is promised: `EventOutput` has a bounded queue/5s receipt and no device ownership, but it does not join an indefinitely blocked OS stdout write. Document and test the exact chosen ownership contract.

Current doctor cancellation drops the collected future via `execute`'s ctrl-C select (`main.rs:644`); tool `kill_on_drop` requests kill but is not proof of reap. A new export that promises all probe children reaped should keep/join the observation owner after stop or add an explicit cancellation API; do not strengthen the old doctor's claim merely by wrapping it in a new file format.

## Existing evidence versus required next tests

Source-only existing fixtures reviewed (not rerun): Native diagnostics tests at927–1178 cover exact module names, loaded/install/effective distinctions, complete sysfs table, bounded reads, executable trust, fixed argv/env, sanitized version shape, timeout/output-limit kill+reap. These are reusable unit/IPC boundaries, not a delivered diagnostic export.

Necessary new software tests should target behavior, not mirror every field assignment:

1. End-to-end projection with hostile sentinel strings in every permitted source String: tool version, error payload, device strings/serial, paths/hosts/profile/principal. Assert exact closed keys/types and absence of sentinels even in failure JSON; reject unsupported schema/unbounded collections. Preserve unknown/denied/unavailable instead of turning them into ready/zero.
2. Source dispatch fixture that records all invoked operations: only Native fixed reads/version probes and one Status; no mutations, Discover, Open/Prepare, Reconcile or loader of private credentials. A helper peer failure must not fall back to root/native mutation. Include broker/root/unauthorized classification without changing policy.
3. Actual file-output tests: existing/symlink/hardlink/FIFO/directory targets, secure final mode, short write/disk error, interruption and destination publication. Verify first error retained and incomplete files cannot be parsed as a successful complete export.
4. Default Native compilation/dependency check separately from secure-transport/all-features. If optional config inspector is implemented, use production decoder/trust boundary with test-only fixture root rather than granting test env overrides in the binary. Test no credentials are read and root/operator results accurately indicate unsupported/not-loaded stages.
5. One focused **real ordinary-UID subprocess suite**, using a prebuilt binary/root-owned packaged tools (no host USB mutation): actual report creation/parse/mode, missing or unsafe helper path, tool availability recorded as observed, stdout consumer failure/backpressure/cancel per promised contract, no logger bytes in report. Snapshot only controlled files and process handles. Do not claim actual helper-root authentication from a UID-only fake peer; root-credential cases require isolated guest or existing IPC fixture.
6. If root/nonroot installed behavior must be accepted, one small disposable guest with the existing installed helper may run export as root and authorized/unauthorized ordinary UID, record exact Status/refusal and unchanged **saved** USB/journal/driver observations. Do not start new USB sessions just for a diagnostic report; do not repeat prior 23 or 15 matrices or relabel their evidence. Real kernel/tools behavior is separate from source/unit proof.
