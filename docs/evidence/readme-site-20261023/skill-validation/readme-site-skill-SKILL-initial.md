# README + project site

Make the project understandable, demonstrable, and usable from verified facts. Default new copy to English; an explicit user or repository language requirement wins. Deliver only the requested artifacts: a README request does not implicitly include a website.

## Establish the facts

- Read repository instructions, current README, manifests, CLI/help or public API, license, existing docs/site, CI, and relevant acceptance evidence. Respect dirty files and ownership. Follow project skills before touching core code; this skill does not authorize product changes.
- Build a small working map: **claim → source/version → verified scope → limitation**. Separate implemented behavior, actual validation, and roadmap. Keep this in working notes unless the task benefits from a saved record.
- Check actual install/release availability and exact commands, flags, features, prerequisites, working directory, and privilege boundary. Do not invent release binaries, package installs, operating-system support, performance, security, or recovery guarantees.
- When a reference project is supplied, inspect its README and site source through available connected tools, then primary-source browsing as needed. Record the revision and useful principles. Adapt hierarchy and storytelling; do not transplant its product claims, branding, code, or assets without license review.

## Choose the deliverable

**README only:** read [README guidance](references/readme.md), improve the entry path, and link to the maintained detail. Do not add a site/framework/deployment workflow.

**README + site:** read both [README guidance](references/readme.md) and [static site guidance](references/site.md). Plan the pair together: README supports starting and evaluating the project; the site presents its actual value and demonstration. Share facts, commands, assets, and terminology without duplicating every technical paragraph.

For a site-only request, preserve README consistency but edit it only within the authorized scope. Reuse the repository's current site/build system; otherwise prefer plain HTML, CSS, local assets, and small optional JavaScript. No framework or asset pipeline is required by this skill.

## Write and build

- Lead with what users can do and one correct way to start. Put maturity and material limitations near the affected promise. Move long matrices, operation manuals, and research chronology behind descriptive links; retain any indispensable setup or safety conditions.
- Use real product screenshots, captured terminal output, or diagrams grounded in the implementation. App-rendered synthetic examples are acceptable when clearly labeled illustrative. If no authentic visual exists, use an accurate diagram or omit the visual; do not fabricate a functioning interface or present a mockup as evidence.
- Use the real project name, tone, license, repository, and platforms. Keep essential navigation, copyable commands, limitations, and links usable without JavaScript. Treat animation, tabs, filters, and copy buttons as optional enhancements.
- Maintain readable contrast, semantic headings, keyboard access, visible focus, useful alt text, responsive layout, and reduced-motion behavior. Test project-subpath URLs and repository/document links separately.

## Verify and hand off

Check README local files/anchors, examples against the actual interface, and README/site claim consistency. For a site, also check local asset resolution, desktop/mobile rendering, keyboard behavior, JavaScript disabled, reduced motion, and repository-subpath hosting. State which checks actually ran and any remaining gaps; a prose outline is not a rendered-site test.

Report changed files, validation, and publishing status succinctly. Creating site files is not proof of a live deployment. Publish or change Pages settings, workflows/permissions, domains, or external services only when authorized by the current task; honor existing authorization without asking again. Do not install tools, trigger releases, commit, or push merely because this skill describes those possible next steps.
