# Installed authentication failures and credential retirement

2026-10-24. Design baseline clean `0c6e4b74b155159722aa65e1b22464ad5621001f`. Proposed test contract; no new runtime result is implied. The preceding increment delivered private diagnostics, 797 software executions and a separate installed WAL-pause scenario. The full Phase 0–7 objective remains active.

## Gap and existing implementation

The original requirements include authentication failures, unauthorized devices, repeated imports and safe resource release. The current six secure QEMU runs use one authorized client identity. `rustusb-transport/src/tls/tests.rs` already exercises missing/unknown/expired/wrong-purpose certificates, names, ALPN and removed pins over real in-memory TLS. The two actual server integrations also have software ACL tests. Those tests do not establish installed-process credential retirement, refusal before a free kernel capability is acquired, or unaffected original USB I/O during hostile connections.

The production contract remains immutable startup credentials/policy. Rustls performs standard chain/time/usage/name verification before leaf-DER pin mapping; removing a pin affects a newly started server, not an existing authenticated stream. Retiring a credential therefore requires cooperative owner cleanup and a real restart. This increment tests that contract, without introducing hot reload, CRLs, OCSP, arbitrary FD revocation or a new cryptographic scheme.

## Independent client and certificates

Product negative clients use protected, role-correct configuration files and actual CLI exits/output. A copied OpenSSL `s_client` is a test-only independent raw-v1 attacker for absent certificate/ALPN and direct IMPORT, not a product bypass. It must verify server trust/name using `-verify_return_error`, fixed TLS 1.3 and explicit ALPN for valid authenticated wire cases. Its `-quiet` mode implies ignored stdin EOF; require the actual server response/close and a bounded process wait, not premature local EOF. No session secrets/key logging, insecure verifier, clock changes or production network are allowed.

The first actual clean `3d7e126` run failed before completing its first refusal batch: the unmapped-client CLI really exited 1 with empty stdout, while the harness's error-text assertion omitted the observed Rustls `peer closed connection without sending TLS close_notify` I/O result. TLS 1.3 client handshake completion can precede server-side principal mapping; `tls/tests.rs` already preserves that distinction. Keep the original FAIL and the actual I/O result. The corrected harness may recognize this exact close text and fixed fatal-certificate alert categories as well as the handshake category; do not widen it to arbitrary I/O failures or describe the close as clean EOF. Standard certificate and mapping causes remain supported by exact fixture/policy/source correlation, not an inferred decrypted server trace. A new clean run must still prove every later refusal, unchanged original resources and actual I/O.

The second actual clean `176fee3` run reached unmapped, expired, wrong-purpose and unknown-CA client failures with actual exit 1 and retained fixed close/alert outcomes. It then failed the harness's text assertion for wrong server name: the shared service intentionally projects a failed server handshake to `permission denied: secure server authentication failed`. Recognize that exact existing product category too, rather than expecting the lower-level transport's Display string to escape the service boundary. Preserve the second FAIL and its later unexecuted stages.

The [OpenSSL 3.0 CA reference](https://docs.openssl.org/3.0/man1/openssl-ca/) specifies explicit certificate start/end dates; use an ordinary CA fixture with an actually expired leaf rather than modifying the guest clock. The [s_client reference](https://docs.openssl.org/3.0/man1/openssl-s_client/) documents verification failure and EOF behavior. Record the actual executable version and copied library identities. These commands support a disposable test CA only, not a production CA recommendation.

## Verdict and limits

The host checkpoints the first FAIL and still collects both guests. A wait timeout or guest exit 0 cannot replace a host failure; every scenario uses fresh evidence and a clean committed source. Record locked build, all selected source/build inputs, generated scripts, actual executable receipts, public certificates/configs, real child waits, kernel/sysfs/helper state, exact wire fixtures, input captures and PCAP. The independent raw checker must verify both epoch-specific original identities rather than forcing the second epoch to equal the first epoch's capabilities.

Run applicable software gates, Python/shell checks and the actual paired matrix. Existing 797/older matrices keep their own revisions; test-only changes do not create new Rust test counts. Real hardware G1/G2, certificate expiry during an already established stream, certificate hot reload/CRL/OCSP, sustained authentication exhaustion, permanent kernel blocking, complete security G3 and later phases remain unfinished unless separately proven.
